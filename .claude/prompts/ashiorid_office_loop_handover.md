# Handover: ashiorid_office live table loops on the same scene

Status: open. Run is STOPPED (manual, idle). Nothing is on air. Fix not yet implemented; awaiting go-ahead on the design in section 5.

## 1. Symptom

The office run (`ashiorid_office_20260929_135927_9c1b`) plays scene after scene in which Nora (tuber_6, Office Manager) arrives at the front entrance in the early morning, asks the Party Member (tuber_7, silent observer) whether they're still there, and repeats "Three things, then I'll let you go." Each new scene restarts the morning from the same arrival beat. The story does not progress.

Observed from the GM log (`docker logs virtualtubers-worker-gm-1`, scene_start / scene_resolve lines):

- `off-hours-arc-n0-n0-004` (the first scene) is played repeatedly. Each play begins with "The emergency strip hums... Nora steps into the dim glow..."
- Later scenes in `off-hours-arc-n0-n1`, `off-hours-arc-n1`, and `first-standup-arc-n0` open with the same entrance and the same "Late night, love?" / "Morning, love" beats.
- Canon goals across different scenes are near-identical, e.g.:
  - "The Party Member looks up from their writing as the Office Manager enters/arrives..." (several variants)
  - "The Office Manager starts setting up the office as the Party Member finishes their late night writing..."
  - "The Party Member and Office Manager exchange a few words before the Party Member heads out..."

## 2. Root causes (verified in code and logs)

### 2a. The GM has no memory of earlier scenes (main cause)

`app/agent_handlers/table_gm.py:405-408` (`context_provider`) builds the GM context with `segment=None, contract=contract`. The only story content the GM receives is:

- the GM identity and gm_blocks (`app/table/gm_context.py`, `build_gm_context`)
- the player sheets
- the current scene contract

Nothing from prior resolved scenes is included. `continuity_in` and `continuity_out` exist on the contract (`app/table/contract.py`), but the GM never sees a running summary, and the arbiter does not carry one forward between scenes. So each scene is generated as if it were the first morning of the office.

Note that `context_provider` also says "the current arc segment" is included, but it passes `segment=None`, so the segment is never rendered. Design rule U8 (`.claude/prompts/agent_dnd_vllm_build_plan.md:27`) says the story should come from the arc plan (Layer 1 `arc_plan` + Layer 2 `brief`/`tree`). That is not wired for the office run.

### 2b. Arc slots are written as independent arrival beats

The contract data comes from `tests/table/fixtures/ashiorid_office_20260929_135927_9c1b.json` (9 artifacts: 1 `arc_plan`, 4 `brief`, 4 `tree`). The `canon_goal` fields are generated per slot, and many slots restate the same entrance. The GM follows each goal literally, so it re-stages the arrival every time.

### 2c. Dedupe only removes exact duplicates

`table_gm.py` `contracts_provider` (around lines 325-330) drops contracts whose `canon_goal` matches exactly (after lowercasing and whitespace normalization). Near-duplicate goals pass through.

### 2d. Contributing: my own restarts replayed the first scene

During debugging I issued `table_run_start from=beginning` twice and restarted the GM container. Both restarts began again at `off-hours-arc-n0-n0-004`, so the first entrance appeared multiple times in the log. This made the loop look worse than the generation alone produces. Per the user, the loop was also visible in the original run. Treat 2d as an amplifier, not the cause.

## 5. Proposed fix (needs approval before implementing)

1. Add a running story summary to the GM context. After each scene resolves, record a compact entry (scene_id, what happened, the state_delta from `scene_resolve`, and which characters are where). Include the last N entries (for example 6) in `build_gm_context` as a "What has already happened" section. Keep it in the arbiter or runtime state, persisted with the position file so it survives restarts.
2. Wire the arc segment. Pass the current segment's `brief`/`tree` into `build_gm_context` as `segment=`, instead of `None`, so the GM knows where in the arc it is.
3. Tell the GM that an entrance already happened. Add a rule to the contract or GM identity: if the previous scene's state_delta already has the Office Manager present, do not restage an arrival; continue from the current state.
4. Dedupe near-duplicate canon goals (for example token-set Jaccard over a threshold) in `contracts_provider`, and log what is dropped.
5. Tests: unit tests for the summary builder and the new context section; a test that two consecutive contracts with the same arrival beat do not both render an arrival in the GM context; a fixture-driven run of the first 3 scenes to confirm the story advances.

Be careful with (1): the GM context is capped by `gm_context_max_chars` (24000), and player sheets are the part that gets shortened first. Make sure the summary is not cut to zero.

## 6. What to verify before saying it's fixed

- Run the first 6 scenes from the fixture on the GM and confirm no scene opens with the Office Manager arriving after the first one.
- Check that `state_delta` from each `scene_resolve` shows progress (for example `office_manager_state` moving from "arrives" to "set up", then to "standup").
- Check the `/table/status` `Next` scene advances each time.
- Test a GM restart mid-run: the summary should come back from the persisted state.
