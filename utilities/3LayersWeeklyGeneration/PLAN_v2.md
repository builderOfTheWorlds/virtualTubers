## Part A — Layer 2 (recursive segmentation)

### Context

The 3-layer generator (`utilities/3LayersWeeklyGeneration/`) currently plans
each 6-hour segment with a **fixed** two-level fan-out: 2a always emits
exactly `chapters_per_segment` (9) chapters, 2b always emits ~19 slots per
chapter. That split exists purely because one segment's full slot list
(~170 entries, ~10.2k tokens) doesn't fit one LLM call — it isn't shaped
around where the story actually needs detail.

The proposal: make this scalable instead of fixed. A segment should be
plannable at whatever depth the content actually needs — a dense stretch (a
spine scene, a fork point, heavy state dependency) recurses further, a quiet
stretch (ambient downtime) stays shallow or is planned directly. This
generalizes the existing 2a/2b split from a hard-coded 2 levels into an
arbitrary-depth tree, driven by a deterministic word-budget check rather
than trusting a model's self-assessment of its own output density (matching
this codebase's existing philosophy — see `sensitivity_budget`,
`density_floor`, the fork convergence validator: guards are deterministic,
never trust-based).

Per the earlier discussion, **only the segment→...→slot portion becomes
recursive.** Layer 1 (`plan_arc.py`, arc→segment) stays exactly as built:
it's serial by nature (each batch needs the previous batch's
`continuity_out`), cheap (~20 min total), and already implemented/tested —
there's no efficiency to gain by touching it, and the story-density variance
being described lives inside a segment, not across segments.

### Decisions taken this session

| # | Decision | Rationale |
|---|---|---|
| 1 | Exhausted expand → **degrade the node to a forced leaf**, not drop it | Dropping a depth-1 node with weight 0.4 silently costs ~40% of a segment against today's ~11%. A forced leaf reuses the escape hatch `max_depth` needs anyway; content survives at coarser granularity. |
| 2 | **Continuous work queue**, not BFS level-by-level | A frontier containing one branch node idles 3 of 4 workers and gates everything behind it. Submitting children the moment a parent resolves keeps the pool busy; per-node checkpointing gives *better* crash safety than per-level (lose one node, not one level). |
| 3 | Prompts carry the **full ancestor summary chain** | At depth 1 the parent *was* `arc_segment`, so passing the node alone was complete. At depth 3 the intermediate summaries vanish and a leaf sees only the 6-hour synopsis plus its own one-liner — losing exactly the context the recursion exists to add. |
| 4 | **Rewrite the specs and regenerate via the qwen worker**, using `qwen3.8:27b` as the coding model | Same workflow that built these modules. `qwen3.8:27b` is pulled and available; `runner.py --model` already parameterizes it. |

### Design

#### The node model (replaces the fixed chapter concept)

Every unit below the segment root — whether it ends up looking like today's
"chapter" or goes deeper — is the same record shape:

```python
{
  "node_id": str,        # see "Node ids" below
  "parent_id": str | None,
  "order": int,           # 0-based, contiguous among siblings
  "depth": int,           # 0 = root (the segment itself)
  "title": str,
  "summary": str,
  "continuity_in": str,
  "continuity_out": str,
  "target_words": int,    # this node's share of airtime words
  "target_slots": int,    # derived: round(target_words / (words_per_take * takes_per_slot))
  "kind": "branch" | "leaf" | None,   # None = not yet resolved
  "forced": bool,         # True when max_depth or expand-failure forced the leaf
  "children": [node_id, ...],          # once kind == "branch"
  "slots": [...] | None,               # once kind == "leaf"
}
```

The root node is `arc_segment` wrapped with `target_words =
config["segment"]["target_words"]` — everything else about `arc_segment`
(spine_scenes, synopsis, continuity) is passed through to every leaf's
prompt regardless of depth, exactly as `build_slot_prompt` already does
today (spine ground truth isn't chapter-scoped currently either).

##### Node ids

`f"{parent_id}-n{order}"`, so root `seg-01` → child `seg-01-n2` →
grandchild `seg-01-n2-n0`. **Not** `{parent}.{order}`: `worklist.take_path`
(`worklist.py:50`) uses the prefixed `slot_id` as a literal directory name,
and dotted path components read as file extensions to every tool that later
globs that tree. Slot ids become `f"{node_id}-{slot_id}"` — the same
prefixing rule as today, just with a longer prefix.

#### The recursion trigger — deterministic, not model-trusted

A node is a **leaf** (planned directly into slots) once `target_slots <=
segment.tree.max_leaf_slots` (default 19, matching today's per-chapter
count). Otherwise it's a **branch**: one LLM call asks for child nodes, each
carrying a `weight` — its relative share of the parent's `target_words` —
instead of an equal split. This weight is the actual "scale up/down"
mechanism: a dense child (spine scene, high state-dependency) gets a bigger
weight → bigger `target_words` → likely still oversized after distribution
→ recurses again. A quiet child gets a small weight → small `target_words`
→ likely already leaf-eligible → no further calls.

Two things force a leaf regardless of size, both logged at WARNING and both
setting `forced: True`:

1. **`max_depth` reached** (default 4).
2. **Expand exhausted its retries** (decision 1). The node still gets a slot
   call for its full `target_slots` — past the size a single call
   comfortably covers, but it produces content rather than a hole.

A `min_node_words` floor (default 2000) is enforced by the validator on the
weight distribution, not requested of the model — a child whose
weight-derived word share falls under the floor fails validation and the
whole expand call is retried, the same retry-then-degrade pattern above.

#### `generation.yaml` — replace `chapters_per_segment` with a `tree:` block

```yaml
segment:
  ...
  target_words: 53600
  target_slots: 170
  tree:
    max_leaf_slots: 19    # node this size or smaller is planned directly (today's ~19/chapter default)
    max_children: 12      # fan-out cap per expand call
    max_depth: 4          # safety cap below the segment root; hit + still oversized -> forced leaf, WARNING
    min_node_words: 2000  # anti-fragmentation floor, enforced by the validator
    leaf_density_floor: 0.80   # a leaf returning fewer than this * target_slots fails validation
  concurrency: 4
  max_attempts: 2
  sensitivity_budget: 0.40
  density_floor: 0.80
```

A uniform-weight run (every child gets equal weight) reproduces today's
shape almost exactly — root splits into ~9 leaf children of ~19 slots each,
1 expand + 9 leaf calls — so the default behavior doesn't regress; the new
behavior only appears when weights are lopsided.

**Knob interlock.** These four values can be set mutually infeasible (e.g.
`min_node_words` above the leaf threshold in words means every expand fails
validation, retries, degrades, and the run quietly produces one giant leaf
per segment). `validate_tree_config(config) -> List[str]`, called once at
the top of `plan_segment`, checks:

- `max_children >= 2`
- `min_node_words * 2 <= max_leaf_slots * words_per_take * takes_per_slot`
  (a branch node must be splittable into at least two floor-legal children)
- `max_depth >= 1`, `max_leaf_slots >= 1`, `0 < leaf_density_floor <= 1`

Problems raise `SegmentPlanError` — this is operator error, not model
error, and should fail loudly at startup rather than degrade silently.

#### `src/segment_schema.py` — generalize chapter/slot to node/expand/leaf

Renames and additions (pure functions, no I/O, same style as today):

- `SYSTEM_PROMPT_EXPAND` (was `SYSTEM_PROMPT_CHAPTERS`) — asks for child
  nodes with `{order, title, summary, continuity_in, continuity_out,
  weight}`, explains that weight reflects how much is happening in that
  slice and should scale with it.
- `SYSTEM_PROMPT_LEAF` (was `SYSTEM_PROMPT_SLOTS`) — unchanged in spirit;
  same ambient/spine slot shape as today.
- `parse_children` (was `parse_chapters`), `parse_slots` (unchanged).
- `leaf_eligible(target_slots, config) -> bool`.
- `derive_target_slots(target_words, config) -> int` — pulls
  `budget.measured_baseline.words_per_take` and `dialogue.takes_per_slot`,
  the same formula the top-level `target_slots` in generation.yaml already
  documents. Note the derived per-child slot counts are **not** guaranteed
  to sum to the parent's `target_slots` (independent rounding); words
  reconcile exactly, slots drift by at most one per child. `density_floor`
  absorbs this at the segment level and it is not worth reconciling twice.
- `distribute_words(children, node, config) -> children` — normalizes
  weights to sum 1, multiplies by `node["target_words"]`, rounds,
  reconciles the rounding remainder onto the largest child so the sum is
  exact (same "must sum exactly" discipline as fork `carry_out`
  elsewhere), and sets each child's derived `target_slots`.
- `validate_tree_config(config) -> List[str]` — the interlock check above.
- `validate_children(children, node, config) -> List[str]` (was
  `validate_chapters`) — required keys, contiguous 0..N-1 order, count
  within `[1, max_children]`, `weight` a positive number, non-empty
  `summary`, **non-empty `continuity_in`/`continuity_out` strings**, and
  every distributed child word share `>= min_node_words` (computed via
  `distribute_words` inside validation, so a floor violation is caught
  before any child node is created).

  *Deliberately not validated:* semantic continuity chaining (child 0's
  `continuity_in` actually matching the parent's). It is prose; there is no
  deterministic check for it, and this codebase does not add trust-based
  guards. Chaining is handled on the prompt side instead — siblings are
  generated in one call and see each other, and the ancestor chain (below)
  carries the parent's continuity down.
- `validate_slots(slots, pack, vocab, config, node=None)` — **correction to
  the earlier draft: today's `validate_slots` does not check slot count at
  all.** `target_slots` appears only in `build_slot_prompt` and the
  segment-level density check. Under recursion that gap widens (more leaves,
  more chances to under-deliver, one aggregate warning at the very end), so
  this adds one check: when `node` is given and
  `len(slots) < node["target_slots"] * leaf_density_floor`, that's a problem
  string → retry. Everything else about the function is unchanged.
- `build_expand_prompt(pack, arc_segment, ancestors, node, config, problems)`
  (was `build_chapter_prompt`) — renders the segment synopsis, then each
  ancestor's title + summary in depth order, then this node's
  synopsis/continuity/`target_words`, an expected-children guideline
  (`ceil(node.target_slots / max_leaf_slots)` capped at `max_children`), and
  asks for a `weight` per child.
- `build_leaf_prompt(pack, arc_segment, ancestors, node, config, problems)`
  (was `build_slot_prompt`) — same content as today's slot prompt plus the
  ancestor chain, slot count from `node["target_slots"]`.
  `ancestors` is `List[node]` root-exclusive, ordered shallow→deep; empty
  at depth 1, which makes these prompts byte-comparable to today's for a
  uniform run.
- `merge_brief(arc_segment, tree, config) -> Dict` (was chapter-keyed) —
  DFS-walks the tree in `order` (preserves the "drain in arc order"
  property), flattens every leaf's slots into the same
  `{segment_id, order, loop, hours, synopsis, continuity_in,
  continuity_out, carry_in, carry_out, slots: [...]}` shape `worklist.py`
  already reads. Each slot's provenance tag becomes `node_id` (replacing
  `chapter_id`). Adds an optional `nodes:` summary (id, depth, kind,
  forced, target_slots, actual slot count) so a human reading `brief.yaml`
  by hand at Stage 2 can see the tree shape a run actually produced.
- `check_sensitivity_budget` — unchanged, but see the call-site change below.

#### `src/plan_segment.py` — a continuous work queue over the tree

1. **Startup**: `validate_tree_config` → raise on operator error.
2. **Resume**: load `tree.yaml` if present; else seed the root node from
   `arc_segment`. Path is derived, **not** a new argument —
   `out_path.with_name("tree.yaml")` — so `plan_segment`'s signature is
   unchanged and no caller or test fixture has to grow a parameter.
3. **Drain**: one `ThreadPoolExecutor(max_workers=
   config["segment"]["concurrency"])` for the whole run. Seed it with every
   unresolved node; as each future completes, classify and submit
   immediately rather than waiting for a level to finish:
   - `depth >= max_depth` → forced leaf (WARNING, `forced: True`)
   - `leaf_eligible(...)` → leaf
   - otherwise → branch
   - **branch task**: `build_expand_prompt` → LLM → `parse_children` →
     `validate_children` → `distribute_words`, retried to `max_attempts`.
     Exhausted → WARNING, reclassify this node as a forced leaf and
     resubmit it as a leaf task (decision 1).
   - **leaf task**: `build_leaf_prompt` → LLM → `parse_slots` →
     `validate_slots` (now including the per-leaf density check), retried to
     `max_attempts`. Slot ids prefixed with `node_id`. Exhausted → ERROR +
     empty `slots` for that node; this is the only remaining skip path and
     it costs at most one leaf's worth of slots, same as today.
   - Because a branch task enqueues new work, the drain is a
     `while pending:` loop over `as_completed`-style bookkeeping rather than
     a single `with executor:` block — new futures must be admissible after
     the first wave.
4. **Checkpoint after every completed node**: write `tree.yaml`, recompute
   and write `brief.yaml` via `merge_brief`. A crash loses at most one
   node — strictly better than today's "at most one chapter", and better
   than the level-batched alternative.
5. **Final**:
   - `check_sensitivity_budget` on the **flattened segment slot list**, not
     per leaf. Per-leaf was equivalent to per-chapter (~19 slots) before;
     under a tree a 6-slot leaf with 2 flag-sensitive slots reads as 33% and
     warns on noise. The segment-level figure is the one the budget was
     written about (`generation.yaml`: "max fraction of a segment's slots").
     Per-leaf remains as a DEBUG line only.
   - Same segment `density_floor` check as today (flattened slot count vs.
     `target_slots * density_floor`).
   - Tree-shape summary log line: nodes total, leaves, forced leaves,
     depth range, slots, nodes skipped.

### Merged from PLAN.md — Layer 2 items the implementation dropped

PLAN.md's Layer 2 pseudocode (`PLAN.md:311-382`) specifies more than
`segment_schema.py` shipped. These are folded into the prompt-builder and
guard rewrites rather than left as a second pass.

**M1 — The parallelism precondition, generalized (`PLAN.md:337-343`).** This
is the invariant that keeps all 28 segments concurrent, and the tree must not
break it:

> Cross-segment continuity flows through `arc_plan.yaml` — which Layer 1 has
> already written — and *never* through a sibling segment's `brief.yaml`.

Generalized to the tree: **a node's context comes from its ancestor chain and
from the single expand call that created it and its siblings — never from a
cousin's resolved slots, and never from another segment.** Siblings agree
because one call wrote all of them; cousins never need to agree, because both
descend from summaries that were already reconciled higher up. This is what
makes decision 2's continuous work queue sound — any two unresolved nodes can
run at the same instant regardless of position. Restate it verbatim in the
rewritten spec files; it is the one property whose violation collapses Layer 2
into a serial chain without failing a single test.

**M2 — Prompt content the shipped `build_slot_prompt` dropped.** PLAN.md
specs the slot prompt as synopsis + continuity + **relevant lore** (each
`spine_scenes` entry's `pack.scene(id).lore`, plus `ambient_focus` scenes'
lore) + cast roster + each spine scene's **actual `enter_narration` and beat
text** + an explicit `target_words` / `target_slots` stop condition. The
shipped builder (`segment_schema.py:379`) has only: chapter summary, slot
count, state flags, cast, spine `enter_narration`.

The lore omission is issue #3's live symptom and the cheapest to fix.
`vocabulary.unknown_lore` (`vocabulary.py:74`) validates every declared stem
against `pack.lore` and its error message even names the legal set — but the
prompt never shows the model that set, so a leaf call is a guess-and-retry on
lore by construction. `build_leaf_prompt` must render the legal stems the
same way it already renders legal state keys.

Add to `build_leaf_prompt`, all of it already reachable from `pack` and the
node:

- legal lore stems (`sorted(pack.lore.keys())`), presented as a closed set
- for each `arc_segment["spine_scenes"]` id: `enter_narration` **and** beat
  text, not just the narration line
- `ambient_focus` scenes' lore, where the arc segment declares them
- the node's `target_words` alongside `target_slots`, as an explicit stop
  condition — PLAN.md is specific that a concrete count beats an open-ended
  "sequence of beats", and under the tree that count is per-node rather than
  per-segment

**M3 — Event roll points (`PLAN.md:377`, D15).** "Mark each chapter boundary
as an event roll point" was never implemented and chapters are now gone. Per
the D19 decision, roll points become **leaf boundaries**: `merge_brief` emits
`roll_points: [node_id, ...]` in DFS order alongside `nodes:`, and event
seeds derive from `(events.seed, run_id, node_id)` instead of `chapter_id`.
Layer 2 only *emits* the list — nothing consumes it until `src/events.py`
exists, and that is out of scope here. Consequence to record in D15: leaf
sizes vary, so "~252 rolls over 168 h" stops being arithmetic and becomes an
estimate bounded by `max_leaf_slots`.

**M4 — The density guard should measure words, not slot count.** N5's
post-L2 guard is "segment slots sum to within ~80% of `target_words`"; the
shipped check compares `len(brief["slots"])` against `target_slots *
density_floor`. Those agreed when every slot was one ninth of a uniform
chapter. Under variable-size nodes they don't, and the word figure is now
directly computable — every node carries `target_words`. Keep the slot-count
check (it is what catches a leaf returning nothing) and **add** the word
check: `sum(leaf.target_words for leaf in leaves)` against
`segment.target_words * density_floor`, reported in the same WARNING.

**M5 — Sensitivity budget: "mark the segment for re-brief" (`PLAN.md:371`).**
The shipped code only logs a WARNING; nothing records that the segment should
be re-briefed, so a 168-hour run's over-budget segments are discoverable only
by grepping logs. `merge_brief` writes `needs_rebrief: true` into
`brief.yaml` when the flattened segment mix exceeds `sensitivity_budget`, and
the Part B CLI grows `--rebrief` to re-plan exactly those segments. Cheap,
and it makes the guard actionable instead of advisory.

**M6 — Intermediate artifacts.** PLAN.md specs `chapters.yaml` plus
`chapters/<chapter_id>/slots.yaml` per chapter, merged into `brief.yaml` once
complete. `tree.yaml` replaces both: it holds the node records *and* each
leaf's slots, so it is the single working checkpoint and `brief.yaml` is
purely derived. Per-node slot files would multiply with depth for no gain now
that resume reads one file.

### Build workflow (decision 4)

The qwen worker writes only `target_files` and reads `test_files` as
context (`prompting.py:72`, `prompting.py:97`). **The tests must therefore
exist before the worker runs.** Order:

1. Hand-write `config/generation.yaml`'s `tree:` block.
2. Hand-write `tests/segment_helpers.py`, `tests/test_segment_schema.py`,
   `tests/test_plan_segment.py` against the design above.
3. Rewrite `tools/qwen_worker/specs/3layers_segment_schema.yaml` and
   `3layers_plan_segment.yaml` — goal prose, the node model, the work-queue
   contract, the forced-leaf degradation rule.
4. `python tools/qwen_worker/runner.py --model qwen3.8:27b preflight`
5. `python tools/qwen_worker/runner.py --model qwen3.8:27b run
   tools/qwen_worker/specs/3layers_segment_schema.yaml` → review → `promote`
6. Same for `3layers_plan_segment.yaml` (it imports the schema module, so it
   must run second).
7. Change `ollama_client.DEFAULT_MODEL` to `qwen3.8:27b` if it should be the
   standing default rather than a per-invocation flag.

`qwen3.8:27b` is pulled and available locally. `runner.py --model` already
parameterizes it (`runner.py:242`); `DEFAULT_NUM_CTX` is 32768 and these two
specs plus their test files are the largest prompts in the spec set — if the
worker truncates, raise `--num-ctx` before blaming the model.

## Part B — `main.py` and test mode

Nothing in the utility is runnable today: `main.py` does not exist, so Layer 1
and Layer 2 are reachable only from tests. This is the smallest piece of work
in the doc and it gates the value of everything else.

Per CLAUDE.md, `main.py` is a thin orchestrator — argparse, calls into `src/`,
minimal logic of its own. Every `src/` module already exposes a plain function
for it to call and none carry their own argparse.

```
main.py --stage {arc|segment|dialogue|all}
        [--pack PATH] [--config PATH] [--segments ID[,ID...]]
        [--model-profile NAME] [--test-mode] [--rebrief]
        [--dry-run] [--log-level LEVEL]
```

- `--stage arc` → `plan_arc.plan_arc(...)`, writes `arc_plan.yaml`.
- `--stage segment` → for each segment id, `plan_segment.plan_segment(...)`.
  Default segment set is every segment in `arc_plan.yaml` without a
  `brief.yaml`; `--rebrief` selects those whose brief carries `needs_rebrief`
  (M5) and re-plans them from scratch.
- `--stage dialogue` → Part C.
- `--stage all` → arc → segment → dialogue, resumable at each layer.
  `config.validate_profile_for_stages` (`config.py:124`) already exists for
  the `--model-profile` + `--stage all` interaction and issue #10 wants that
  documented, not re-solved — call it and surface its error.
- `--dry-run` on the segment stage prints the tree that *would* be planned
  from the config's budget arithmetic (root `target_slots`, expected children,
  expected depth) without an LLM call. Cheap, and the fastest way to sanity
  check a `tree:` block after changing a knob.

### Test mode (`PLAN.md:231`)

`--test-mode` requires `--segments <one-id>` (to keep it cheap) and runs
**every** profile under the active layer's `models:` map rather than just
`active_model`. Output goes to `<output.dir>/<pack>/_test/<stage>/<profile>/`
— separate and non-resumable, so it can never pollute a real `arc_plan.yaml`,
`brief.yaml`, `tree.yaml` or manifest. After each profile it prints one line:
model, wall-clock seconds, word/slot count.

The mechanism already exists — `config.resolve_profile(config, layer,
profile_name)` returns a flat dict and `concurrent_llm.from_profile` builds a
client from it, so test mode is a loop calling the same layer function once
per name from `config.profile_names(layer)`. No layer function changes.

This is the practical answer to "is `qwen3.8:27b` good enough to plan with, or
does Layer 2 need `hermes3:70b`" — the same question decision 4 raises for the
*coding* model, asked about the *planning* model, and answerable in one
segment's GPU time instead of by argument.

### The local take function

```python
def generate_take(improviser, unit, config):
    """One take for one WorkUnit. Never raises; [] is a failed attempt."""
    scene = Scene(id=unit.slot_id, prompt=unit.slot["prompt"],
                  lore=unit.slot.get("lore", []))
    improviser.recent = []
    improviser.update_context(scene=scene,
                              loop=unit.slot.get("loop", 1),
                              carry=unit.conditions)
    beats = improviser.generate_scene(scene)
    return [_beat_to_dict(b) for b in beats]
```

Two things this pins down that nothing currently states:

- **`loop` comes from the brief, not the take number** — issue #6's fix. The
  segment's `loop` is already on `brief["loop"]` and `merge_brief` carries it;
  thread it onto each slot (or read it from the brief in the closure).
- **`WorkUnit.conditions` reaches the model through `carry`.**
  `update_context(scene, carry, loop)` (`improviser.py:29`) is the *only*
  context channel, and `generate_scene` renders `Loop N` plus each carry
  key/value into the user prompt (`improviser.py:210-213`). So
  `{"helen-wounded": True}` and `{"mood": "tense"}` both ride the carry
  channel and render as key/value lines. Nothing in PLAN.md said how a
  computed condition became prompt text; this is the answer, and it is worth
  a test — `conditions_for` producing a mood dict that never reaches the
  prompt would leave every conditioned take silently identical to its neutral
  sibling.

Retries are the pool's job (`max_attempts`), not this function's — hence no
attempt loop, unlike `_generate_take`.

### Wiring

```
load pack, config; resolve the dialogue profile -> one shared PooledOllamaClient
segment_ids = args.segments or every segment with a brief.yaml
units = worklist.build_worklist(output_root, segment_ids, config)   # the resume
log the estimate: worklist.estimate_seconds(units, seconds_per_take, concurrency)
stats = pool.run_pool(
    units,
    worker_factory=lambda: LLMImproviser(pack, shared_client, ...),  # ONE PER THREAD
    generate=lambda worker, unit: generate_take(worker, unit, config),
    writer=lambda unit, beats: (_write_take(...), _append_manifest(...)),
    concurrency=config["dialogue"]["concurrency"],
    max_attempts=config["dialogue"]["max_attempts"],
    breaker=CircuitBreaker(**config["dialogue"]["breaker"]))
guard: every ambient slot has exactly one take with conditions {}
report: takes written, words, per segment; neutral-take coverage; failures
```

- **Spine slots are never generated.** `kind: spine` is scripted canon;
  `units_for_segment` should already exclude them — confirm with a test rather
  than assuming, since a spine slot reaching the pool would overwrite authored
  content.
- **The neutral-take guard is hard (issue #14).** Every ambient slot must end
  with exactly one take whose `conditions` is `{}`. A run finishing without it
  has produced a library that can dead-air, which is the one failure the whole
  `neutral_takes` design exists to prevent. Failing the guard is a non-zero
  exit, not a warning.
- **The stinger pass is out of scope.** It depends on `events.yaml`, which
  N2b has not produced. Leave the hook (`--stingers` rejected with a clear
  "requires events.yaml, not yet built") rather than a stub that silently
  does nothing.

### `generation.yaml` — the circuit breaker has no config block

`pool.CircuitBreaker(window, failure_rate, min_samples)` (`pool.py:53`) takes
three parameters and **none of them appear in `generation.yaml`**. A
multi-day unattended run is exactly where a breaker matters (PLAN.md:649: a
dead ollama produces empty takes forever without raising), so it needs real,
reviewable values rather than constants buried in `main.py`:

```yaml
dialogue:
  ...
  breaker:
    window: 50           # rolling sample size
    failure_rate: 0.5    # trip above this fraction failing
    min_samples: 20      # never trip before this many samples
```
